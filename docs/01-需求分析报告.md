## 1. 项目命名

### 1.1 定名

> **中文名：手脉**  
> **英文名：HandPulse**  
> **Slogan：看见你的手在怎么用力。**

**命名释义**

| 字 | 指向                                                                   |
| - | -------------------------------------------------------------------- |
| 手 | 采集对象不是"键盘"，而是手。键盘、鼠标、手柄都只是手的延伸形态，一个词覆盖全部输入设备，也为未来的指环、手套、握力器等硬件留出语义空间 |
| 脉 | 脉搏：连续、有节律、可读。它天然指向"按分钟聚合的强度曲线"，而不是逐条按键日志 —— 这正是本产品最核心的数据哲学           |

**为什么这个名字适合这个产品**

1. **不锁死在键盘上**。叫「键X」的产品，做鼠标热力图和手柄摇杆分析时会显得名不副实。
2. **有健康联想但不越界**。"脉"暗示身体信号，但没有"医""诊""疗"的字面承诺，规避医疗器械宣传的合规风险。
3. **可延展为硬件品牌**。`HandPulse Pad`、`HandPulse Ring`、`HandPulse Core` 都成立，符合"软件先行、硬件补生理信号"的路线。
4. **英文短、可搜索、域名友好**。`handpulse` 组合词，商标检索冲突概率低于 `keypulse`、`tapflow` 这类已被大量占用的词根。

### 1.2 备选方案与取舍

| 备选名            | 优点           | 否决原因                  |
| -------------- | ------------ | --------------------- |
| 键息 KeyBreath   | 有呼吸感，气质好     | "键"字把鼠标/手柄排除在外        |
| 腕迹 WristTrace  | 精准指向手腕劳损     | 过于贴近"伤病"，暗示医疗属性       |
| APM Lab        | 玩家一秒理解       | 太工具化，无法承载健康与硬件叙事      |
| 手况 HandScope   | 与"体况"同构，现代感强 | "况"字读音偏硬，口语传播差        |
| 指迹 FingerTrace | 具象           | 手柄摇杆主要由拇指/掌心驱动，不全是"指" |

### 1.3 品牌延展命名规则

| 形态       | 名称                | 说明                               |
| -------- | ----------------- | -------------------------------- |
| 采集内核（开源） | HandPulse Core    | Rust 库 + CLI，可被第三方复用，是隐私可信的证明物   |
| 桌面应用     | HandPulse Desktop | 主产品                              |
| 手机应用     | HandPulse Mobile  | 伴生应用，定位"看 + 提醒 + 教练"，不做采集（见 7.7） |
| 自研硬件     | HandPulse Gear    | 外设产品线                            |
| 数据格式     | `.hpulse`         | 导出包格式，含 schema 版本号               |

## 2. 背景与问题定义

### 2.1 目标用户的三个真实痛点

游戏玩家对自己的手，其实处于一种"感觉驱动"的盲区：

**痛点一：键位和灵敏度靠玄学调**  
换了一套键位、调了 DPI，感觉"好像顺手了"，但没有任何证据。玩家在论坛上争论"高敏还是低敏""WASD 还是 ESDF"，全靠个人体感。**没有人知道自己哪个手指承担了最多的动作。**

**痛点二：训练强度没有计量单位**  
一天打 6 小时排位，中间真正高强度操作了多久？什么时候手开始"掉线"（APM 下降、失误率上升）？玩家只能回忆"今天打到手酸"。**手部负荷没有像心率、步数那样的日常指标。**

**痛点三：不适感出现得太晚**  
腱鞘炎、腕管综合征、网球肘在玩家群体中高发，但早期信号（持续高频单键、长时间不间断输入、左右手严重失衡）在发生时是完全无感的。等到疼，已经是积累期之后。**缺少一个"提醒你还活着"的低成本哨兵。**

### 2.2 现有方案为什么不够用

| 现有方案                       | 做到了什么         | 缺什么                                       |
| -------------------------- | ------------- | ----------------------------------------- |
| WhatPulse / KeyCounter 类   | 全局键鼠计数、总里程    | 只有累计总量，无时间维度、无健康视角、无热力图；Windows 老架构，长期无维护 |
| ActivityWatch / RescueTime | 应用与网页时间追踪     | 粒度在"应用"，看不到手；不采集按键                        |
| 在线键盘检测站（keyboardtester 类）  | 实时按下高亮、键位冲突检测 | 刷新即清零，不留任何历史；只有"现在"，没有"趋势"                |
| 游戏内 APM 统计                 | 单局 APM 均值     | 只覆盖自家游戏；只有均值，看不到分布与爆发段；不含鼠标位移与手柄          |
| 智能手环 / 手表                  | 全身活动量、心率      | 完全看不到手部精细动作，对"敲击负荷"零感知                    |
| 表面肌电（sEMG）设备               | 真实的肌肉负荷       | 需要贴电极、进实验室，消费场景不可用                        |

**空白地带已经很清楚了：**

> 一个**长期、细粒度、以"手"为单位、跨设备统一**的行为记录层。  
> 它不追求单次的精确测量，而是追求**连续数月的可比趋势**。

这句话是本项目的立项根基。所有功能取舍都应回到它：凡是破坏"长期连续"的（比如要求用户每次手动开启、要求联网登录），都要砍掉；凡是增强"可比性"的（基线、对比、同比），都要加强。

### 2.3 我们要解决的三个问题

| 编号 | 问题                | 解法方向                                    |
| -- | ----------------- | --------------------------------------- |
| R1 | 记录必须**无感**，不能打断游戏 | 后台常驻、系统级输入流旁路读取、CPU 占用 < 1%、全屏游戏时不弹任何窗口 |
| R2 | 数据必须**结构化到能存一年**  | 只存聚合桶，不存事件流；分级保留策略；单年存储 < 300 MB        |
| R3 | 结论必须**可解释**       | 每个指标都能回答一个玩家能听懂的问题；不做黑箱评分               |

### 2.4 明确的非目标（Non-Goals）

这一节和功能清单同等重要，用于防止范围蔓延。

| 不做                    | 原因                                      |
| --------------------- | --------------------------------------- |
| 医疗诊断、疾病预测、康复处方        | 无医学依据，法律风险极高。产品定位为"行为统计工具"              |
| 采集输入内容（字符、文本、密码、聊天记录） | 隐私红线。技术上通过"只取物理扫描码 + 只存计数"从架构层面杜绝       |
| 员工监控 / 家长监控 / 远程上报    | 与"个人自用"定位冲突，且触碰《个人信息保护法》敏感区             |
| 游戏内实时教练、操作评分、外挂式建议    | V1 不做。需要游戏内数据（位置、经济、命中率），采集成本与反作弊风险都不划算 |
| 云端账号、跨设备同步            | V1 不做。本地优先是隐私卖点，也是开发成本的减项               |
| 键位冲突检测、全键无冲测试         | 属于"键盘评测"场景，与本产品长期记录的主线不同（原型阶段作为副产品顺带提供） |
| 屏幕录制 / 截图 / OCR       | 零容忍。任何图像采集都会摧毁产品的信任基础                   |

## 3. 用户与使用场景

### 3.1 用户画像

**画像 A：硬核竞技玩家（核心用户，占比预估 55%）**

- 18–28 岁，FPS（CS2、Valorant、Apex）或 MOBA（LoL、Dota2）为主
- 日均 3–8 小时，周末更长；有明确的"训练"意识
- 关心：APM、灵敏度、键位效率、外设手感
- 焦虑点：手腕不适、手指僵硬，见过职业选手的伤病新闻
- 付费意愿：中高（愿意为外设花 500+ 元，对软件付费敏感但在 30–60 元区间可接受）
- 关键诉求：**别卡、别弹窗、别上传我的数据**

**画像 B：休闲玩家（占比预估 30%）**

- 每周 10 小时左右，多品类混玩，键鼠 + 手柄混用
- 关心："我这个月到底玩了多少""我的手柄是不是该换了"
- 关键诉求：**打开就能看懂，不需要学习成本**

**画像 C：手部敏感 / 康复期玩家（占比预估 15%）**

- 已有轻微不适，或医生建议控制使用强度
- 关心：连续时长、休息提醒、强度趋势
- 关键诉求：**能设上限、能被提醒、数据能拿给医生看（导出）**
- 注意：这类用户最容易把产品当医疗器械用，免责声明必须前置且醒目

### 3.2 核心场景剧本

**场景 S1：赛后复盘（高频，每日）**

```
21:40  打完 5 局排位，关闭游戏
21:41  打开手脉，首页显示"今晚 2 小时 12 分，峰值 APM 386（第 3 局 21:03）"
21:42  点进"数据"页，7×24 热力图显示今晚集中在 19:00-21:30
21:43  折线图上看到第 4 局开始 APM 从 340 跌到 210 —— "那局我确实打崩了"
       → 得到结论：2 小时后操作强度自然衰减，与主观感受吻合
```

**场景 S2：键位调优（中频，每周/每次改键后）**

```
用户把蹲键从 Ctrl 改到 Shift
→ 一周后打开键盘热力图对比：Ctrl 区块从深红变浅蓝，Shift 变深
→ 左右手负荷比从 2.1:1 改善到 1.6:1
→ 结论：这次改键确实让左手小指减负了（可视化证据）
```

**场景 S3：训练负荷管理（中频，赛季/训练期）**

```
连续 7 天 HLI（手部负荷指数）都在 78 以上
→ 应用在第八天首页给出"本周手部负荷连续偏高，建议安排一天低强度"
→ 用户点开趋势图，看到本周鼠标移动距离是上月均值的 1.8 倍（换了低灵敏度）
```

**场景 S4：长期趋势观察（低频，季度级）**

```
季度报告：本季度总输入 124 万次，日均 1.4 万，较上季度 -12%
鼠标累计移动 41 公里，手柄使用占比从 12% 升到 34%（开始玩手柄游戏了）
夜间（23 点后）使用占比 26%，较上季度上升
→ 结论：整体强度下降但作息变差
```

## 4. 产品定位与边界

### 4.1 一句话定位

> **手脉是你手部的运动手环：不打扰你，只在你回头看的时候，告诉你这双手经历了什么。**

### 4.2 能力边界

| 维度   | 能做                      | 不做                         |
| ---- | ----------------------- | -------------------------- |
| 测量对象 | 按键次数、点击次数、位移量、按住时长、间隔分布 | 输入内容、手指力度、肌肉状态、姿态（V1 无硬件时） |
| 时间尺度 | 10 秒桶 ~ 年度趋势            | 单次操作的精确回放                  |
| 结论性质 | 行为统计、相对基线的强度对比、习惯描述     | 生理测量、医学判断、能力评估（"你适合打职业"这类） |
| 数据流向 | 本机写入、本机读取、用户主动导出        | 自动上传、第三方共享、广告画像            |

### 4.3 关于"监控"这个词的说明

需求原文使用"监控"描述用途。在落地时必须做一次措辞转换，原因有二：

1. **法律层面**："监控"在中文语境下默认指向"一方监视另一方"，容易落入《个人信息保护法》中"处理他人个人信息需单独同意"的严格场景。
2. **产品层面**：目标用户是玩家本人，数据的所有者、使用者、受益者是同一个人。这是 **self-quantification（自我量化）**，不是 surveillance（监视）。

**规范用语（对外文案与文档统一）**

| 禁用          | 改用              |
| ----------- | --------------- |
| 监控你的操作      | 记录你的手部使用        |
| 采集用户行为      | 统计本机输入频次        |
| 上传使用数据      | 导出数据（用户主动触发）    |
| 健康评估 / 健康报告 | 使用强度概览 / 手部负荷参考 |

若未来推出面向战队/网吧的版本（V2+），必须独立设计：可见的采集指示灯、全员知情同意书、管理员不可关闭的"员工可查看自己的数据"入口、数据保留期限。这一条写进产品原则，不可协商。

```
HandPulse Desktop

│   ├── 个人基线（30 日滚动）
│   ├── HLI 手部负荷指数
│   ├── 规则引擎（阈值提示）
│   └── 习惯画像（6 维标签）
├── FR-04 可视化
│   ├── 折线图（分时强度 / 多日趋势 / 对比）
│   ├── 直方图（键位排行 / 时段分布 / 间隔分布）
│   ├── 热力图（7×24 / 日历 / 键盘布局 / 鼠标屏幕网格 / 手柄布局）
│   └── 明细表（分时明细 / 下钻）
├── FR-05 报告与导出
├── FR-06 提醒
├── FR-07 设置与数据管理
└── FR-08 扩展（硬件 / 插件 / 开放 API）
```

### 5.2 FR-01 采集引擎

#### 5.2.1 采集对象与粒度矩阵

| 输入设备 | 采集项                                                 | 粒度   | 是否落盘               |
| ---- | --------------------------------------------------- | ---- | ------------------ |
| 键盘   | 每个物理键的按下次数                                          | 按桶聚合 | 是                  |
| 键盘   | 长按次数与累计按住时长（过滤系统自动重复）                               | 按桶聚合 | 是                  |
| 键盘   | 组合键（Chord）触发次数（如 Ctrl+C）                            | 按桶聚合 | 是                  |
| 键盘   | 按键间隔直方图（<50 / 50–100 / 100–200 / 200–500 / >500 ms） | 按桶聚合 | 是                  |
| 键盘   | 逐次按下的键码序列                                           | 实时   | **否**（仅内存，供实时视图使用） |

#### 5.2.2 聚合机制（本产品的核心技术设计）

需求原文的关键约束：**"不记录有序的事件流，只记录某分钟、某几十秒内的使用次数情况"**。

这不是一个存储优化，而是一个**架构级隐私承诺**。落地方式如下：

```
内核 HID 事件（键盘/鼠标/手柄）
        │  仅旁路监听，不拦截、不修改、不注入
        ▼
[ Ring Buffer ]  环形缓冲，容量 = 2 × tick（默认 1s）
        │  只存"发生了什么类型"，不落地
        ▼
[ Aggregator ]  1s tick 时读取并清空缓冲
        │  累加到当前桶的计数器（原子操作，无锁）
        ▼
[ Bucket ]  10s / 30s / 60s 桶（用户可配，默认 60s）
        │  桶关闭时才序列化写入
        ▼
[ SQLite ]  已聚合、无可还原性
        │
        ▼
[ 实时视图 ]  ← 消费者直接订阅 Ring Buffer（内存），不经过磁盘
```

**三个必须遵守的规则：**

1. **原始事件永不落盘**。Ring Buffer 是唯一的原始事件持有者，生命周期以毫秒计，进程退出即消失。
2. **实时视图与历史数据走两条不同的路**。键盘高亮、鼠标轨迹这类"当下"的展示全部来自内存订阅，历史页面全部来自聚合桶。二者不共享存储。
3. **间隔信息用直方图桶代替序列**。要算"连击率""输入节奏"，理论上需要事件序列；我们用 5 个间隔区间的计数器来近似。代价是丢失精确节奏曲线，收益是数据不可还原为输入内容 —— 这个交换是值得的，并且必须在文档里写明代价。

#### 5.2.3 桶配置与保留策略

| 层级     | 粒度                 | 默认值 | 保留期  | 用途         |
| ------ | ------------------ | --- | ---- | ---------- |
| L0 实时  | 1s tick            | 内存  | 不落盘  | 实时视图、当日累加  |
| L1 细桶  | 10 / 30 / 60 s（可配） | 60s | 30 天 | 分时折线、爆发段识别 |
| L2 小时桶 | 1 h                | 固定  | 2 年  | 长期趋势、同比    |
| L3 天桶  | 1 d                | 固定  | 永久   | 日历热力图、年度报告 |

默认值取 60s 的理由：玩家的"一局"通常 15–40 分钟，60s 粒度足以刻画一局内的起伏；同时把年存储量压到 300 MB 以内。需要更细粒度的用户（如研究型用户）可调到 10s，代价是容量 ×6 且仅保留 7 天。

#### 5.2.4 会话识别

玩家的核心分析单位是"一局游戏"，而不是"一天"。识别策略（三级回退）：

1. **自动**：前台进程白名单（用户可维护）+ 全屏状态 + 持续输入 > 60s → 判定为游戏会话
2. **半自动**：检测到已知游戏进程时，在通知区显示"正在记录 CS2"，用户可点"标记为训练赛"
3. **手动**：快捷键（默认关闭）开始/结束标记

会话只存：开始时间、结束时间、进程名（哈希可选）、聚合指标。**不存窗口标题**（标题可能含聊天对象名、文件名）。

#### 5.2.5 设备识别

- 读取设备描述符中的 VID / PID / Product String，用于"这把键盘"与"那把键盘"的区分
- 不读取序列号（可唯一识别个人，属敏感标识）
- 手柄额外读取：连接方式（USB/蓝牙）、电量（若可读）、死区漂移基线

### 5.3 FR-02 指标体系

**指标设计三原则：**

1. **每个指标必须回答一个玩家会问的问题**（见"回答什么问题"列）
2. **优先用玩家已有的词汇**（APM、DPI、cm/360），不自造黑话
3. **绝对值不如相对值**：所有强度指标默认同时给出"与个人 30 日基线的比值"

### 5.4 FR-03 评估层（非医疗）

#### 5.4.1 设计原则：只和自己比

不使用"通用健康标准"，原因：
- 不存在针对"按键负荷"的权威医学阈值
- 玩家之间的基线差异巨大（职业选手日均 8 小时是常态，上班族 1 小时就偏高）
- 一旦引入"标准值"，产品就会被理解为医疗建议

**做法**：所有强度指标用该用户**过去 30 日的滚动分布**做归一化。显示的永远是"你比平时高多少"，而不是"你超标了"。

#### 5.4.2 HLI 手部负荷指数

```
HLI = 100 × Σ (wᵢ × fᵢ)     fᵢ ∈ [0, 1]

f1 强度     = clamp( 当日 APM_P95 / P90(APM_P95, 30d) )        w1 = 0.25
f2 连续     = clamp( 最长连续输入时长(min) / 90 )               w2 = 0.20
f3 休息缺失 = clamp( 1 − 当日休息次数 / 期望休息次数 )           w3 = 0.20
f4 夜间     = clamp( 夜间输入分钟 / 当日总分钟 × 3 )             w4 = 0.15
f5 失衡     = clamp( |左手−右手| / (左手+右手) × 3 )             w5 = 0.10
f6 鼠标     = clamp( 鼠标里程 / P90(鼠标里程, 30d) )             w6 = 0.10
```

其中 `期望休息次数 = 活跃小时数 × 3`（即每小时 3 次、约每 20 分钟一次的节奏）。

**分档与文案**

| 区间 | 标签 | 建议文案 |
|---|---|---|
| 0–39 | 轻松 | 今天手部负担不大 |
| 40–59 | 正常 | 与你近一个月的常态相当 |
| 60–74 | 偏重 | 今天强度高于你的常态，注意中途活动手腕 |
| 75–89 | 高负荷 | 连续多天高负荷时，建议安排低强度日 |
| 90–100 | 极高 | 今天的输入强度接近你的历史高位 |

**必须随分数一起展示的免责声明（原文固定，不可改）**

> 手脉记录的是你的输入行为，不是你的身体状况。该指数由按键频次、连续时长等行为数据合成，用于和**你自己的历史**做对比，不具备医学意义，不能用于诊断、治疗或预防任何疾病。如出现疼痛、麻木、无力等症状，请咨询专业医师。

#### 5.4.3 规则引擎（提示规则）

| 规则 | 触发条件 | 级别 | 提示语 |
|---|---|---|---|
| R-01 | 连续输入 ≥ 50 min 且无 ≥ 5 min 停顿 | 建议 | 已连续操作 50 分钟，活动一下手腕和手指 |
| R-02 | 单小时 APM > 个人 P95 × 1.3 | 提示 | 本小时强度明显高于你的常态 |
| R-03 | 22:00–06:00 的输入占当日 > 30% | 提示 | 今天大部分操作在深夜，作息偏移会影响恢复 |
| R-04 | 左右手比 > 2.5:1 且持续 3 天 | 提示 | 左手承担了大部分动作，可考虑把部分键位换到右手侧 |
| R-05 | 单个非移动键占比 > 12% | 提示 | 某个键被高频使用，检查键位设计或是否存在误触 |
| R-06 | 鼠标里程 > 个人 P95 × 1.5 | 提示 | 今日鼠标移动量偏高，可检查 DPI / 灵敏度设置 |
| R-07 | 连续 7 天 HLI ≥ 75 | 建议 | 本周负荷持续偏高，建议安排一天低强度 |
| R-08 | 手柄扳机半按占比 > 60% | 提示 | 扳机长期处于半按状态，可调整扳机行程或死区 |
| R-09 | 摇杆静止漂移 > 阈值 | 提示 | 手柄摇杆可能存在漂移，建议校准 |

**干扰控制**：全屏应用运行时，R-01/R-02 的弹窗降级为"静默记录，退出全屏后汇总提示"。这一条是玩家的硬需求，写在验收标准里。

- **粒度自适应**：范围 ≤ 2 天用分钟桶，≤ 60 天用小时桶，> 60 天用天桶。用户可手动覆盖

#### 5.5.3 图表设计约束

- 热力色阶必须过色盲检查（约 8% 男性玩家有红绿色觉异常）：使用**明度递进 + 色相偏移**的双通道，而非单纯红→绿
- 折线图最多同时展示 3 条线，超过则用"堆叠面积"或拆分小图
- 所有 Y 轴默认从 0 开始（避免视觉夸大）；用户在设置里可切换"自适应"

### 6.2 表结构

```sql
-- 元数据
CREATE TABLE meta (
    key         TEXT PRIMARY KEY,
    value       TEXT NOT NULL
);  -- schema_version, install_id(随机UUID，不关联硬件), dpi_config ...

-- 设备
CREATE TABLE device (
    id            INTEGER PRIMARY KEY,
    kind          TEXT NOT NULL,          -- keyboard | mouse | gamepad
    vid           INTEGER,
    pid           INTEGER,
    product_name  TEXT,
    first_seen    INTEGER NOT NULL,
    last_seen     INTEGER NOT NULL
);

-- 键位/按钮定义（布局可扩展）
CREATE TABLE key_def (
    layout        TEXT NOT NULL,          -- qwerty-104 | qwerty-87 | xinput | ...
    key_id        INTEGER NOT NULL,
    label         TEXT NOT NULL,          -- 'W' / 'LMB' / 'A(btn)'
    hand          TEXT,                   -- L | R | none
    finger        TEXT,                   -- pinky|ring|middle|index|thumb
    row           INTEGER,                -- 用于布局渲染
    col           INTEGER,
    width_units   REAL DEFAULT 1.0,
    PRIMARY KEY (layout, key_id)
);

-- L1 细粒度桶（核心表，稀疏存储：只写非零键位）
CREATE TABLE bucket (
    ts            INTEGER NOT NULL,       -- 桶起点 unix 秒
    granularity   INTEGER NOT NULL,       -- 10 | 30 | 60
    device_id     INTEGER NOT NULL,
    session_id    INTEGER,
    total_actions INTEGER NOT NULL,
    payload       BLOB NOT NULL,          -- zstd(JSON): {"keys":{30:42,...},"hold_ms":{...},
                                          --              "chord":18,"gap_hist":[12,40,88,150,60],
                                          --              "streak_ms":42000}
    PRIMARY KEY (ts, granularity, device_id)
);
CREATE INDEX idx_bucket_ts ON bucket(ts);

-- 鼠标/手柄专用桶（字段固定，不塞 JSON，便于聚合查询）
CREATE TABLE pointer_bucket (
    ts            INTEGER NOT NULL,
    granularity   INTEGER NOT NULL,
    device_id     INTEGER NOT NULL,
    clicks_l      INTEGER DEFAULT 0,
    clicks_r      INTEGER DEFAULT 0,
    clicks_m      INTEGER DEFAULT 0,
    clicks_side   INTEGER DEFAULT 0,
    wheel_up      INTEGER DEFAULT 0,
    wheel_down    INTEGER DEFAULT 0,
    move_px       INTEGER DEFAULT 0,
    move_cm_x10   INTEGER DEFAULT 0,      -- 乘 10 存整数，避免浮点
    peak_speed    INTEGER DEFAULT 0,      -- px/s，桶内峰值
    fast_segments INTEGER DEFAULT 0,      -- 甩枪段计数
    grid_hits     BLOB,                   -- 32×18 计数，稀疏编码
    PRIMARY KEY (ts, granularity, device_id)
);

CREATE TABLE pad_bucket (
    ts            INTEGER NOT NULL,
    granularity   INTEGER NOT NULL,
    device_id     INTEGER NOT NULL,
    btn_counts    BLOB NOT NULL,          -- {0:120, 1:88, ...}
    stick_travel  INTEGER DEFAULT 0,      -- 归一化行程累计
    stick_max     INTEGER DEFAULT 0,
    trigger_hist  BLOB,                   -- [深度4档时长]
    idle_drift    INTEGER DEFAULT 0,
    PRIMARY KEY (ts, granularity, device_id)
);

-- 聚合层
CREATE TABLE agg_hour (
    hour_ts   INTEGER NOT NULL,
    device_id INTEGER NOT NULL,
    metrics   BLOB NOT NULL,              -- 预计算的指标快照
    PRIMARY KEY (hour_ts, device_id)
);

CREATE TABLE agg_day (
    day       TEXT NOT NULL,              -- 'YYYY-MM-DD'（本地时区）
    metrics   BLOB NOT NULL,              -- HLI、各指标汇总、画像标签
    PRIMARY KEY (day)
);

-- 会话
CREATE TABLE session (
    id          INTEGER PRIMARY KEY,
    started_at  INTEGER NOT NULL,
    ended_at    INTEGER,
    process     TEXT,                     -- 可空
    label       TEXT,                     -- 用户自定义：排位/训练/休闲
    metrics     BLOB
);
```

**为什么用 JSON BLOB 而不是宽表**：键位有 104+ 个，宽表会变成 300 列的稀疏表，SQLite 的行开销远大于稀疏 JSON。用 zstd 压缩后的 JSON，单个桶约 200–400 字节，写入更快，schema 演进也更灵活。

### 6.3 存储估算

| 项 | 计算 | 结果 |
|---|---|---|
| 单个键盘桶 | 活跃键 ~25 个 × (key_id 2B + count 4B) + 元数据 ≈ 250 B（压缩后 ~120 B） | 120 B |
| 单个鼠标桶 | 固定字段 ~64 B + 网格稀疏 ~80 B | 150 B |
| 每分钟合计（键鼠） | 120 + 150 | 270 B |
| 每日 | 270 B × 1440 | ≈ 380 KB |
| 每年（L1 60s） | 380 KB × 365 | ≈ 139 MB |
| 年度汇总 L2+L3 | 8760 小时桶 + 365 天桶 | < 3 MB |
| **一年总量** | | **≈ 145 MB** |

若用户选择 10s 粒度：L1 扩容 6 倍（≈ 830 MB/年），故 10s 桶强制只保留 7 天（≈ 16 MB 常驻）。


**结论**：单机 SQLite 完全够用，无需引入时序数据库。这也让"数据在你自己的硬盘上"这句话是字面意义上的真实。

## 7. 技术方案

### 7.1 总体架构

```
Layer 0  输入源
         Windows: Raw Input(WM_INPUT) / XInput / HID
         macOS  : IOHIDManager / GameController
         Linux  : evdev / hidraw
         硬件   : USB-HID / BLE-GATT（未来）
              |
Layer 1  设备适配层  DeviceProvider (统一 trait) → MetricSample 流
              |
Layer 2  聚合层      Aggregator: 1s tick 环形缓冲 → 增量计数（无锁原子）
              |
Layer 3  持久层      BucketWriter: 10s/60s 桶 → SQLite(WAL) + 分级保留
              |
Layer 4  查询层      Query API: 本地 HTTP/WS(127.0.0.1) + Tauri command
              |
Layer 5  展示层      React 18 + TypeScript + ECharts
                     桌面(Tauri) / 未来 Web 看板 / 手机 companion（复用组件）
```

**核心分层原则**：Layer 1–3 构成 `HandPulse Core`（纯 Rust，无 UI 依赖），可以被 CLI、GUI、未来的硬件固件工具、第三方应用同时复用。这一层是产品的真正资产。

### 7.2 技术选型

#### 7.2.1 采集内核语言

| 候选 | 优势 | 劣势 | 结论 |
|---|---|---|---|
| **Rust** | 无 GC（无卡顿尖峰）、内存安全、单二进制、跨平台 FFI 成熟、`windows`/`core-graphics`/`evdev` 生态完备、易嵌入 Tauri | 学习曲线陡、编译慢 | **采用** |
| C++ | 平台 API 最贴近、性能上限高 | 内存安全风险（常驻进程崩溃=用户信任崩塌）、跨平台构建痛苦 | 备选（仅特定 HID 解析） |
| Go | 开发快、并发好 | 有 GC（虽已优化，但常驻低延迟场景仍有抖动）、cgo 调用平台 API 繁琐 | 不采用 |
| C# / .NET | Windows 极佳 | macOS/Linux 分发与体积劣势，用户需装运行时 | 不采用 |

#### 7.2.2 应用外壳

| 候选 | 体积 | 内存 | 复用性 | 结论 |
|---|---|---|---|---|
| **Tauri 2** | ~10 MB | ~80 MB | 前端是标准 Web，可复用到 Web/手机 | **采用** |
| Electron | ~150 MB | ~250 MB | 最成熟 | 不采用（"别占我内存"是玩家敏感点） |
| 原生（Qt/egui） | 小 | 小 | UI 复用性差，图表能力弱 | 不采用（图表是核心体验） |

#### 7.2.3 存储与图表

| 层 | 选型 | 理由 |
|---|---|---|
| 主存储 | SQLite（WAL 模式） | 零运维、单文件、跨平台一致、易导出 |
| 压缩 | zstd（每桶独立） | 压缩比高、解压快、可随机读 |
| 分析加速（可选） | DuckDB 附挂 SQLite | 年报表需要跨百万行聚合时启用，避免手写索引 |
| 图表 | ECharts | 热力图/日历图/雷达图开箱即用，中文文档完善，Canvas 渲染性能好 |
| 轻量图表 | uPlot（备用） | 10 万点级折线时替换 ECharts，保持 60fps |
| 状态管理 | Zustand | 轻、无样板代码 |
| 样式 | Tailwind + CSS 变量 | 深色主题优先，便于主题切换 |

### 7.3 三端采集实现矩阵

| 平台 | 键盘 | 鼠标 | 手柄 | 所需权限 | 反作弊风险 |
|---|---|---|---|---|---|
| **Windows 10/11** | `RegisterRawInputDevices` + `RIDEV_INPUTSINK` 隐藏消息窗口，取 `RAWKEYBOARD`（含扫描码、设备句柄） | 同上，取 `RAWMOUSE`（原始位移、按键 flags） | `XInput`（轮询 125–250Hz）→ 回退 `DirectInput8` / Raw HID | 无（标准用户即可） | **低**（用户态只读，无注入无驱动） |
| **macOS 12+** | `IOHIDManager` + `IOHIDManagerRegisterInputValueCallback`，取 usage page 0x07 | 同上，usage page 0x01（X/Y/wheel/buttons） | `GameController.framework`（`GCController`） | **Input Monitoring**（TCC）+ 首次运行引导 | 不适用 |
| **Linux (X11/Wayland)** | `evdev` 读 `/dev/input/event*`，`EV_KEY` | `evdev` `EV_REL`/`EV_KEY`/`EV_ABS` | `evdev` js 接口 → 回退 SDL3 | `input` 组 或 udev 规则（安装时配置） | 不适用 |

**关键实现说明**

1. **坚决不用全局低级钩子**（`SetWindowsHookEx(WH_KEYBOARD_LL)`）。原因：
   - 会被多数反作弊（EAC、BattlEye、Vanguard）判定为可疑行为
   - 处于输入链路中，任何延迟或异常都会直接影响用户操作手感
   - 容易被杀毒软件误报为键盘记录器
   Raw Input 是**旁路只读**：事件已经进入系统队列后才被我们观察，不改变输入路径。

2. **macOS 的 IOHIDManager 优于 CGEventTap**：前者能拿到设备身份（多设备区分）与原始 HID usage，且不参与事件分发；后者在 `listenOnly` 模式下虽然安全，但拿不到设备维度信息。

3. **Linux 必须走 evdev 而非 X11 XRecord**：Wayland 已是主流，XRecord 在 Wayland 下不可用；evdev 在内核层，与显示服务器无关，反而是三端里最稳的路径。代价是需要 udev 规则（安装脚本自动写入 `/etc/udev/rules.d/99-handpulse.rules`）。

4. **手柄不要自己解析 HID 描述符**（V1）：HID 报告描述符的解析与各厂商差异是深坑。V1 用 SDL3 Gamepad 做统一抽象（它已处理 XInput / DualSense / Switch Pro 的差异），只在需要"死区漂移"等精细指标时才下沉到平台 API。

### 7.4 反作弊与游戏兼容（专章）

这是本项目**最容易被低估、也最可能致命**的工程风险。目标用户是游戏玩家，而现代竞技游戏普遍部署内核级反作弊。

**风险分级**

| 反作弊 | 严格度 | 对我们的影响 | 应对 |
|---|---|---|---|
| Vanguard（Valorant） | 极高，内核态，开机自启 | 可能阻止任何非白名单的后台输入读取 | 提供"Vanguard 模式"：检测到进程存在时暂停采集，退出后恢复；主动申请 Riot 第三方白名单 |
| EasyAntiCheat（EAC） | 高 | 通常容忍 Raw Input（大量外设软件都在用），但可能标记 | 提交 EAC 白名单申请；提供可关闭的"兼容模式" |
| BattlEye | 高 | 类似 EAC | 同上 |
| 网易/腾讯系保护（如 ACE、TP） | 高，国内特有 | 国内玩家主力场景，需单独测试 | 必须在国服主流游戏上逐个实测 |

**设计对策**

1. **零注入原则**：不注入 DLL、不读写其他进程内存、不安装内核驱动、不修改任何窗口。
2. **零回放原则**：绝不调用 `SendInput` / `keybd_event`（这一条要写进代码评审清单）。
3. **可探测性**：提供一个"兼容性自检"页面，列出检测到的反作弊进程与当前采集状态。
4. **游戏模式**：检测到全屏独占 + 已知反作弊进程 → 自动降级（仅聚合计数，不读设备名，不记录进程名）。极端情况下用户可设为"游戏中完全暂停"。
5. **分发合规**：代码签名证书（EV 证书可减少 SmartScreen 拦截），并向主流反作弊厂商提交白名单申请（这是标准流程，外设厂商都走这条路）。
6. **透明沟通**：官网提供"为什么手脉不会被判定为外挂"的技术说明页，含架构图与"我们不做什么"清单。玩家社区对这类问题极其敏感，主动说明比事后解释成本低得多。

### 7.5 跨平台抽象

```rust
/// 所有输入源（真实设备、自研硬件、回放器）都实现此 trait
pub trait DeviceProvider: Send {
    fn kind(&self) -> DeviceKind;                       // Keyboard | Mouse | Gamepad | Custom
    fn info(&self) -> DeviceInfo;                       // vid/pid/name/connection
    fn poll(&mut self, out: &mut SampleSink) -> Result<()>;
}

/// 聚合器的输入：只有"增量"，没有"事件序列"
pub struct SampleSink { /* 预分配的定长数组 + 原子计数器 */ }

impl SampleSink {
    pub fn key(&self, key_id: u16) { /* fetch_add(1) */ }
    pub fn hold(&self, key_id: u16, ms: u32) { }
    pub fn gap(&self, ms: u32) { /* 落入 5 档直方图 */ }
    pub fn move_px(&self, dx: i32, dy: i32) { }
    pub fn grid_hit(&self, x: u8, y: u8) { }
}

/// 自研硬件只需实现这个 trait，即可复用全部存储与可视化
pub trait HardwareProvider: DeviceProvider {
    fn capabilities(&self) -> Vec<MetricCapability>;    // 握力/sEMG/IMU/温度
}
```

**关键设计**：`SampleSink` 的接口是"增量式"的，**没有任何方法能拿到完整事件序列**。这是把"不记录事件流"从规范变成编译期约束 —— 即使未来有人想加日志功能，也得先改这个接口，会被代码评审拦下。

| 空闲 CPU（无输入） | < 0.2% | 任务管理器 30 分钟均值 |
| 高强度输入 CPU | < 1.5% | 模拟 400 APM 持续 10 分钟 |
| 常驻内存（Core） | < 40 MB | RSS |

| 冷启动到可采集 | < 1.5 s | 计时 |
| 对游戏帧率影响 | 0 帧（不可测） | RTSS 帧时间曲线对比 |

### 7.7 手机端可行性（诚实评估）

这是需求中"手机 App 再议"的技术结论，建议在立项时就明确，避免后期期望错位。

| 平台 | 能否采集全局键鼠 | 可行路径 | 结论 |
|---|---|---|---|
| iOS | **不能**。系统无全局输入监听 API，第三方 App 只能拿到自己窗口内的事件 | ① 连接自研硬件（BLE）读取硬件侧数据；② 系统 Screen Time / DeviceActivity API 只能拿到 App 使用时长；③ 快捷指令手动记录 | 手机端**不做采集**，定位查看端 |
| Android | **很受限**。无障碍服务理论上能监听，但 Google Play 政策对"监听输入"极严，上架风险高；`InputMethodService` 只能覆盖软键盘 | ① 无障碍（不建议，商店风险）；② BLE 硬件；③ 手动记录 | 同上 |

**结论**：HandPulse Mobile 的定位是 **companion（伴生）**，三个功能：
1. 查看桌面端同步过来的数据（本地 Wi-Fi 直连，不经云）
2. 接收提醒（长时间操作 → 手机推送，适合"提醒家人/自己"）
3. 与自研硬件直连（BLE），这是手机上唯一有意义的**采集**路径

这个结论反过来强化了硬件路线的战略价值：**手机端要采集，只能靠硬件。**

### 7.8 自研硬件接入（生态战略）

**为什么硬件是必由之路**

软件层能拿到的只有"行为"（按了多少次、移动多远）。手部健康真正关心的是"生理"（用多大力、肌肉是否持续紧张、姿态是否变形）。这两者之间有本质鸿沟：

| 维度 | 软件可测 | 硬件可测 |
|---|---|---|
| 行为频次 | 是（本产品核心） | 是 |
| 按压力度 | 否 | 是（压力传感器 / 霍尔） |
| 握持姿态 | 否（仅能靠鼠标位移推测） | 是（IMU） |
| 肌肉持续紧张度 | 否 | 部分（sEMG） |
| 手部温度/血流 | 否 | 可测（PPG/温度） |
| 皮肤电（应激） | 否 | 可测（EDA） |

**接入设计**

- 传输优先级：USB HID（免驱、跨平台、低延迟）> BLE GATT（手机友好）> 串口（仅调试）
- 数据格式：与软件端 `MetricSample` 同构，硬件只上报增量，不上报原始波形（延续"不存事件流"原则）
- 指标命名空间：`hw.{device_id}.{sensor}.{metric}`
- 隐私：硬件数据同样只存聚合值；sEMG 等可能涉及生物识别特征的原始信号**默认不存储**，只在本地实时计算特征值

**战略意义**：软件建立用户基数与数据资产 → 硬件补齐生理信号 → 形成"软件+硬件+长期数据"的闭环壁垒。竞品可以抄界面，抄不走用户三年的手部基线数据。

## 9. 合规与伦理

### 9.1 法律适用

| 法规 | 关联点 | 我们的做法 |
|---|---|---|
| 《个人信息保护法》（中国） | 输入内容属个人信息；生物识别属敏感个人信息 | 主动不采集内容；硬件生理信号仅本地计算特征值，不存原始波形；不涉及人脸/指纹/声纹 |
| 《数据安全法》 | 数据分级 | 全部数据留在本机，不构成数据出境 |
| GDPR（若出海） | 数据最小化、可携权 | 最小化（只存计数）、`JSON 导出`即数据可携 |
| 医疗器械监管（NMPA/FDA） | "健康"宣称可能触发医疗器械定义 | 所有文案避免"诊断/治疗/预防疾病"；不使用"健康评分"等表述；明确"非医疗用途" |

### 9.2 产品伦理三条

1. **数据属于产生它的人**。没有"上传即服务改善"的默认勾选，没有"匿名化后可用于研究"的预设。
2. **采集必须可见**。托盘图标常驻、采集时有动效、任何时候一键暂停。暗箱采集是不可接受的。
3. **不制造焦虑**。不用红黄绿三色给用户"打分审判"，不用"你的手正在受损"这类恐吓文案。所有提示都是"参考"语气，且提供关闭开关。

### 9.3 未成年人

玩家群体中有相当比例的未成年人。若未来开放账号或社交功能，需增加监护模式（数据仅本地、关闭所有提醒、家长不可远程查看）。V1 为纯本地工具，天然规避此问题。

## 13. 附录

### 13.1 术语表

| 术语 | 定义 |
|---|---|
| 桶（Bucket） | 一个固定长度的时间片内的聚合计数单元，是系统的最小存储单位 |
| APM | Actions Per Minute，每分钟综合动作数（键 + 鼠标 + 手柄） |
| KPM / MPM | Keys / Mouse actions Per Minute |
| 连续输入时长 | 相邻输入间隔 < 5s 视为连续时的最长片段长度 |
| HLI | Hand Load Index，手部负荷指数（行为合成指标，非医疗） |
| 个人基线 | 用户过去 30 日的指标分布，用于归一化对比 |
| 会话 | 一次连续的游戏/使用片段，由前台进程与全屏状态推断 |
| 物理键位 | 键盘扫描码 / HID usage code 对应的物理位置，与字符无关 |

### 13.2 指标公式汇总

```
KPM          = Σ keys_in_bucket / (bucket_seconds / 60)
APM          = (Σ keys + Σ clicks + Σ pad_buttons) / minutes
APM_P95      = percentile(apm_series, 95)
高强时长      = count(apm > P90(apm, 30d)) × bucket_minutes
左右手比      = Σ keys(L) / Σ keys(R)
键位熵        = −Σ pᵢ·log₂(pᵢ) / log₂(N)      （归一化到 0–1）
连击率        = hist[<100ms] / Σ hist
休息次数      = count(idle_gap ≥ 5min)
鼠标里程(cm)  = Σ move_px / (DPI / 2.54)
HLI          = 100 × Σ wᵢfᵢ                  （见 5.4.2）
```
